# COREDEV-413 — Системный промпт ИИ-задачи в модели BPMN и редакторе процессов

Дата: 2026-08-12. Целевой релиз: Release 2026.3. Исполнитель: anton.ivanov.
Задача в трекере: https://citeck.ecos24.ru/v2/dashboard?recordRef=emodel/ept-issue@COREDEV-413

Связанный план документации: `citeck-ai/docs/plans/20260812-rating-agents-and-ai-docs.md`, пункт Д1 (строка 55, таблица §2.1).

## 1. Суть расхождения

Обработчик внешней задачи `BpmnAiExternalTask` в citeck-ai умеет принимать системный промпт, но записать его в схему нечем: в ecos-process такого свойства нет ни в модели задачи, ни в конвертерах, ни в форме свойств элемента.

Что подтверждено чтением кода:

- `citeck-ai/src/main/java/ru/citeck/ecos/ai/domain/assistant/bpmn/BpmnAiExternalTask.kt:25` — константа `PROP_SYSTEM_PROMPT = "aiSystemPrompt"`; `:39` — чтение `externalTask.extensionProperties[PROP_SYSTEM_PROMPT]` (тип `String?`, без значения по умолчанию). Подписка объявлена с `includeExtensionProperties = true` (`:16`), то есть источник значения — `camunda:properties` элемента, а не переменная процесса.
- `:46-49` — значение прогоняется через ту же подстановку `${переменных}`, что и текст запроса (`BpmnContextUtils.processUserInput`); `:65` — передаётся вторым аргументом в `BpmnAiService.processRequest`.
- `citeck-ai/.../BpmnAiService.kt:58-60` — системное сообщение добавляется в запрос к модели только при непустом значении. Отсутствующее и пустое значение ведут себя одинаково.
- `ecos-process/.../model/ecos/task/ecos/BpmnAiTaskDef.kt` — в модели пять полей: `userInput`, `preProcessedScript`, `postProcessedScript`, `addDocumentToContext`, `saveResultToDocumentAtt`. Поля системного промпта нет.
- Поиск строки `aiSystemPrompt` по всем проектам в `workspace-ctk` (без каталогов сборки) — 0 вхождений. То есть на практике ветка системного промпта в обработчике всегда получает `null`.

Почему значение теряется при сохранении схемы из редактора: ecos-ui дочищает атрибуты `ecos:*`, отсутствующие в форме свойств элемента — `ecos-ui/src/components/editors/ModelEditor/BPMNModeler/patches/features/modeling/cmd/UpdatePropertiesHandler.js:17-25`. Пока поля нет в форме, вписанный вручную `ecos:aiSystemPrompt` будет удалён при первом сохранении из редактора.

## 2. Где проходит значение свойства (цепочка)

1. Форма свойств элемента (артефакт **в ecos-process**, не в ecos-ui): `src/main/resources/eapps/artifacts/ui/form/bpmn/type/bpmn-type-bpmn_EcosTaskAiTask.json`. Ключ поля формы соответствует локальному имени атрибута XML, редактор читает и пишет его как `ecos:<ключ>` (`ecos-ui/.../BPMNModeler/utils.js:52-70`, `ecos-ui/src/pages/ModelEditor/ModelEditor.jsx:629`).
2. Схема ECOS BPMN: атрибут `ecos:aiSystemPrompt` на элементе `bpmn:task` с `ecos:taskType="aiTask"`.
3. Модель ecos-process: `BpmnAiTaskDef`, отображение атрибутов в поля — `io/convert/BpmnConvertations.kt:488-496` (чтение) и `:509-516` (запись).
4. Экспорт в Camunda: `io/convert/camunda/flow/task/CamundaTaskConverter.kt`. Здесь важная развилка — часть свойств уходит в `camunda:properties` (их видит внешний обработчик), часть остаётся атрибутами `ecos:` и обрабатывается внутри ecos-process листенером `engine/camunda/impl/aitask/AiTaskParseListener.kt`. Системный промпт нужен внешнему обработчику, значит его место — `camunda:properties`, рядом с `aiUserInput` (строки 72-88), а **не** в блоке атрибутов на строках 144-147.
5. Обработчик citeck-ai получает значение из `externalTask.extensionProperties`.

## 3. Правки в ecos-process

Каталог: `src/main/java/ru/citeck/ecos/process/domain/bpmn/`

1. `io/EcosBpmnModel.kt` — добавить константу рядом со строками 113-117:
   `val BPMN_PROP_AI_SYSTEM_PROMPT = QName(NS_ECOS_BPMN, "aiSystemPrompt")`.
   Имя атрибута обязано совпадать с константой в citeck-ai посимвольно.
2. `model/ecos/task/ecos/BpmnAiTaskDef.kt` — добавить поле `val systemPrompt: String = ""`.
   Значение по умолчанию обязательно: определения процессов хранятся как `ObjectData` и восстанавливаются Jackson, у ранее сохранённых определений этого поля не будет. В `validate()` ничего не добавляем — системный промпт необязателен.
3. `io/convert/BpmnConvertations.kt`:
   - `convertToBpmnEcosTaskDef()` (строки 488-496) — `systemPrompt = otherAttributes[BPMN_PROP_AI_SYSTEM_PROMPT] ?: ""`;
   - `fillEcosTaskDefToOtherAttributes()` (строки 509-516) — `otherAttributes[BPMN_PROP_AI_SYSTEM_PROMPT] = ecosTaskDef.systemPrompt`.
4. `io/convert/camunda/flow/task/CamundaTaskConverter.kt` — в `ecosTaskDefProperties` (ветка `is BpmnAiTaskDef`, строки 73-87) добавить третий вызов:
   ```kotlin
   properties.addIfNotBlank(
       CamundaPropertyCreator.string(
           BPMN_PROP_AI_SYSTEM_PROMPT.localPart,
           element.ecosTaskDefinition.systemPrompt
       )
   )
   ```
   `addIfNotBlank` для `CamundaProperty` (`BpmnConvertations.kt:189-191`) пропускает пустые значения, поэтому у процессов без системного промпта свойство в схеме не появится и обработчик останется на прежней ветке `null`. Отдельная логика обратной совместимости не нужна.
5. Форма свойств `src/main/resources/eapps/artifacts/ui/form/bpmn/type/bpmn-type-bpmn_EcosTaskAiTask.json` — в панель `panel_ai_request` добавить поле с ключом `aiSystemPrompt` **перед** полем `aiUserInput`: тип `textarea`, `rows: 7`, подписи ru «Системный промпт» / en «System prompt», подсказка о назначении (роль и правила поведения модели) и о поддержке подстановки `${переменной}` — по образцу подсказки у `aiUserInput` (строки 169-172). Поле необязательное, `defaultValue: ""`.

### Чего делать не нужно

- **Правки в ecos-ui не требуются.** Форма приходит с бэкенда по идентификатору `uiserv/form@bpmn-type-bpmn:EcosTaskAiTask`, редактор пишет любой ключ поля в атрибут `ecos:<ключ>` без белого списка. В moddle-схеме `ecos-ui/.../BPMNModeler/moddle/ecosTask.json` из пяти существующих свойств ИИ-задачи объявлено только `aiUserInput`; остальные четыре живут в `$attrs` и сериализуются корректно. Новое свойство ведёт себя так же, объявлять его в moddle не обязательно — и если объявлять, то последовательно все пять, отдельной задачей.
- Правило линтера `ai-task-no-user-input` менять не нужно: оно проверяет только текст запроса.
- `AiTaskParseListener` менять не нужно: системный промпт потребляет внешний обработчик, а не листенер разбора схемы.

## 7. Попутно найденные дефекты

### 7.1. Разные значения по умолчанию у флага «Включить документ в контекст» — исправлено

Состояние: **исправлено в citeck-ai в этой же итерации** (по отдельной просьбе, вне первоначального объёма COREDEV-413).

Суть: при отсутствии свойства ecos-process подставлял `true` (`BpmnConvertations.kt:493`, и так же на ветке агентной задачи), а оба обработчика citeck-ai — `false` (`String?.toBoolean()` на nullable-значении). Заявленное значение по умолчанию — `true`: оно указано и в форме ИИ-задачи (`defaultValue: true`, поле обязательное), и в форме агентной задачи, и в обеих ветках импорта.

Почему выравнивали именно обработчик, а не модель: `true` — это объявленный продуктовый смысл флага, он же в форме, которую видит настройщик процесса.

Оценка риска для уже развёрнутых процессов — низкая. По истории (`git log -S`) свойство `aiAddDocumentToContext` попадает в `camunda:properties` с самого первого коммита ИИ-задачи `a085e93f`, то есть в определениях, прошедших через экспорт ecos-process, оно присутствует всегда, и прежняя ветка «свойство отсутствует» на практике не достигалась. Изменение затрагивает только схемы, собранные вручную или сгенерированные ИИ-ассистентом в обход экспорта.

Почему прежняя ветка недостижима — цепочка из трёх звеньев:
1. Редактор пишет атрибут при любом состоянии галочки. В `ecos-ui/src/pages/ModelEditor/ModelEditor.jsx:623-676` отбрасываются только значения `undefined`, ложные значения проходят и превращаются в строку `"false"`; `BaseModeler.updateProps` (`:180-208`) тоже ничего не фильтрует.
2. Экспортёр всегда добавляет `camunda:property`: `addIfNotBlank` отсеивает только пустое значение (`BpmnConvertations.kt:189-191`), а `addDocumentToContext.toString()` пустым не бывает.
3. Единственная точка развёртывания BPMN в движок — `BpmnProcessDefRecords.kt:550-575`, туда подаётся результат того же экспортёра; Camunda REST наружу не выставлен.

Проверено на локальном стенде (пространство `tdcuosa`, база `citeck_camunda`, таблица `act_ge_bytearray`): среди развёрнутых определений 22 вхождения топика `citeck-bpmn-ai-task` и ровно 22 вхождения `name="aiAddDocumentToContext"`, ресурсов с расхождением количества — ноль. Распределение значений: `true` — 16, `false` — 6, то есть снятая галочка действительно записывается явно, а не приводит к отсутствию свойства.

Отсюда важное следствие для приёмки: наблюдаемое поведение продукта этим исправлением не меняется, приёмочный сценарий через интерфейс поставить нельзя — нужную ветку просто нечем воспроизвести. Гарантию даёт не разовая проверка на стенде, а тесты `BpmnIOTest` (см. ниже): пока они зелёные, свойство доходит до движка всегда.

Дополнительная тонкость про умолчание `?: true` при импорте: оно срабатывает только когда атрибута нет совсем. Дочистка в `ecos-ui/.../UpdatePropertiesHandler.js:17-25` подставляет пустую строку, и `"".toBoolean()` даёт `false`, то есть очищенный атрибут читается как «выключено», а не как умолчание.

Изменения:
- `citeck-ai/.../bpmn/BpmnAiExternalTask.kt` — `?.toBoolean() ?: true` вместо `.toBoolean()`, с комментарием о межпроектной договорённости;
- `citeck-ai/.../bpmn/BpmnAgentExternalTask.kt` — то же самое;
- новый тест `citeck-ai/src/test/java/ru/citeck/ecos/ai/domain/assistant/bpmn/BpmnAiExternalTaskDocumentContextTest.kt` — три случая: свойство отсутствует, `true`, `false`. Проверено, что на старом коде падает ровно первый случай;
- три случая в `ecos-process/src/test/java/ru/citeck/ecos/process/domain/bpmn/io/BpmnIOTest.kt`, закрепляющие предпосылку со стороны ecos-process: экспорт в Camunda содержит `camunda:property` с этим именем при значении `true`, при значении `false` и даже когда в исходной схеме атрибута нет вовсе. Тестовые схемы — `src/test/resources/test/bpmn/elements/aitask/`. Это первые тесты ИИ-задачи в проекте.

## 7а. Внимание при реализации: что изменилось в ИИ-задаче к 2026-08-13

Раздел переписан: прежнее предупреждение о конфликте с веткой `feature/COREDEV-159` устарело.

Ветка COREDEV-165 доведена и **больше не добавляет третий тип задачи**. Отдельный тип
`aiAgentTask` убран, вместо него у обычной ИИ-задачи появилось необязательное поле `agentRef`,
а топик внешней задачи выбирается в `CamundaTaskConverter` по его заполненности. Поэтому конфликта
двух почти одинаковых веток условия в `convertToBpmnEcosTaskDef` и `fillEcosTaskDefToOtherAttributes`
не будет — ветка `ECOS_TASK_AI` там одна.

Что из этого следует для COREDEV-413:

1. **`BpmnAiTaskDef` уже имеет шестое поле** `agentRef` со значением по умолчанию. Системный промпт
   добавляется рядом, по тому же образцу (значение по умолчанию обязательно — ранее сохранённые
   определения этого поля не содержат).
2. **Тесты уже есть, новый файл заводить не нужно.** Круговое преобразование формата ECOS покрыто
   `BpmnEcosTaskDefConvertationsTest`, экспорт в Camunda и выбор топика — случаями в `BpmnIOTest`
   (`test/bpmn/elements/aitask/`). Планировавшийся в разделе 4 `BpmnAiTaskIOTest.kt` создавать
   не надо, случаи по системному промпту дописываются в эти два файла.
3. **Форма свойств изменилась**: перед `panel_preprocessing` появилась панель «AI Агент» с полем
   `aiAgentRef`. Поле системного промпта по разделу 3.5 по-прежнему идёт в `panel_ai_request`.
4. **Новое решение, которого в исходном плане не было.** Системный промпт и выбранный агент
   конфликтуют по смыслу: у агента своя инструкция, она и есть его системное сообщение. Два
   системных промпта одновременно — это либо молчаливое затирание одного другим, либо склейка,
   и настройщик процесса не увидит, что победило. Поэтому при реализации COREDEV-413 нужно
   осознанно выбрать поведение и зафиксировать его: скрывать поле системного промпта, когда агент
   выбран (условная видимость Formio), либо явно оговорить приоритет в подсказке и в документации.
   Без этого получится настройка, которая иногда ничего не делает.
